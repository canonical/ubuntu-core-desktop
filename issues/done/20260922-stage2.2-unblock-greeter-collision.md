# Stage 2.2 unblock: scope snap-run drop-ins away from the GDM greeter

Date: 2026-09-22 (continuation of `20260922-split-core26-desktop-base-snap.md`)

## Impact / Priority

High. This is the single thing blocking Stage 2.2 (route host-exec'd
units through snap run) and therefore everything downstream — the
2.4/2.5 content-interface split and the 2.6 verification gate. The
concrete symptom: the GDM greeter session runs the same gsd-* systemd
user units as the real user session, and snap confinement rejects the
greeter's dynamic home under /run/gdm3/home, so those units could not
be routed through snap run while the greeter was up.

## What we found (verified against source, not just the Stage 2.2 summary)

The Stage 2.2 submission framed the greeter collision as an
architectural blocker requiring Stage 3A (GDM out of the base). That is
WRONG. The codebase already contains a proven, one-line mechanism to
solve exactly this problem.

1. The real blocker is NOT "snap-confine can't mount the greeter HOME".
   The actual error is:

       "cannot update snap namespace: ... cannot use invalid home directory
        /run/gdm3/home/gdm-greeter: permission denied"

   That comes from isPlausibleHome() in snapd's
   cmd/snap-update-ns/user.go — it is a plain open() of the home dir
   failing with EACCES, NOT a /home/ vs /root/ path whitelist. (The
   /home/ /root/ whitelist DOES exist, in
   cmd/snap-confine/user-support.c setup_user_data(), but it is a
   separate, later check and is not what fires first here.)

2. The greeter session runs as the `gdm` user (confirmed in
   core-base-desktop/hooks/002.1-add-gdm.chroot: "runs on the host as
   the gdm user, separate from the confined ubuntu-desktop-session").

3. The codebase ALREADY uses `ConditionGroup=!gdm` to make a unit skip
   the greeter session. See core-base-desktop/hooks/002.1-add-gdm.chroot
   lines ~60-75: it writes /etc/systemd/user/<unit>.d/70-gdm-skip.conf
   with `[Unit] ConditionGroup=!gdm` for screencast-service and
   ibus-portal-service, precisely because "their snap confinement
   rejects GDM's dynamic home under /run/gdm3/home as outside /home".

   => The fix for the gsd-* units is the SAME pattern: add
      `ConditionGroup=!gdm` so the unit only runs in the real user
      session, never the greeter. The greeter keeps its own unconfined
      gsd-* (fine — the greeter is a separate, lower-trust session that
      does not need per-app confinement).

4. The templated units (org.gnome.Shell@ubuntu, gnome-session-manager@
   ubuntu) are ALREADY correctly instance-scoped to @ubuntu (commit
   3583997 in core-base-desktop). They do NOT need ConditionGroup — the
   @ubuntu instance already excludes the @gdm greeter instance. Only
   the NON-templated gsd-* units (16 of them) need the ConditionGroup
   fix.

## The plan (smallest verifiable steps, one at a time)

### Step 1: verify mechanism

Confirm ConditionGroup=!gdm is the right condition for the gsd-* units.
The greeter runs as user `gdm`; the existing 70-gdm-skip.conf already
uses `ConditionGroup=!gdm` and is known to work for
screencast/ibus-portal. Low risk, but confirm the gsd-* units are
actually instantiated in the greeter session (they should be, since the
greeter is a full gnome-session).

### Step 2: add ConditionGroup to the 16 gsd-* drop-ins

This is mechanical. Add `ConditionGroup=!gdm` to the 16 gsd-* drop-ins
in core-base-desktop/static/usr/lib/systemd/user/
org.gnome.SettingsDaemon.*.service.d/core-override.conf (append a
[Unit] section alongside the existing [Service] section). Do NOT touch
the templated @ubuntu units.

### Step 3: re-apply the snap-run ExecStart overrides

Re-apply the snap-run ExecStart= overrides for the gsd-* units (via the
image-build test harness, or directly in core-base-desktop static/),
now that ConditionGroup=!gdm protects the greeter. Verify ONE gsd-*
unit first (e.g. gsd-keyboard): starts, confined label via
/proc/<pid>/attr/current, no new denials, and the GREETER still comes
up (login screen renders).

### Step 4: gnome-shell slot fix (independent of the greeter)

The gnome-shell snap-run app aborts with "Failed to bind X11 socket"
because the x11/wayland slots are on the MAIN ubuntu-desktop-session
app, not the gnome-shell app. KDE already does this correctly:
plasma-kwin-wayland (the KWin compositor) declares
`slots: [wayland, x11-server, desktop]`. Fix = add the same slots to
the gnome-shell app in
ubuntu-desktop-session-snap/snap/snapcraft.yaml. NOTE: GNOME currently
uses `x11` (not `x11-server`); verify which slot name is correct for
the bind permission before committing.

### Step 5: complain-mode pass

Once one gsd-* and gnome-shell route cleanly, run a complain-mode pass
(aa-complain) on the generated per-app profiles to enumerate the
remaining confined<->unconfined D-Bus peer gaps, and fold them into the
snapd interfaces (systemd_user_control.go etc.). This is the third
"blocker" from the submission, and it is just missing rules, not
architecture.

### Step 6: commit

Commit the verified changes to core-base-desktop (drop-ins) and
ubuntu-desktop-session-snap (slots), then proceed to 2.3 (package
manifest extraction).

Ordering note: Step 4 (gnome-shell slots) is independent of Steps 1-3
(greeter). They can be done in parallel. Step 5 depends on both.

## Open questions / risks

- Is `x11` vs `x11-server` the right slot for gnome-shell's Xwayland
  bind? KDE uses `x11-server`; GNOME's main app currently uses `x11`.
  Confirm which grants the bind permission.
- The greeter's gsd-* units will now be UNCONFINED (they already are,
  via the //&unconfined stacked label). This is acceptable — the
  greeter is a separate session and does not need per-app confinement.
  Flag this as a known, accepted gap rather than a regression.

## The exact fix (proven, three parts in one drop-in)

    /etc/systemd/user/org.gnome.SettingsDaemon.Keyboard.service.d/<name>.conf
      [Unit]
      ConditionGroup=!gdm
      [Service]
      ExecStart=
      ExecStart=/snap/bin/ubuntu-desktop-session.gsd-keyboard
      AppArmorProfile=

Critical gotcha #1: the base snap's core-override.conf sets
`AppArmorProfile=snap.ubuntu-desktop-session.ubuntu-desktop-session`.
If left in place, it STACKS on top of snap run's own profile, producing
the //&unconfined label (NOT the clean per-app label). The
`AppArmorProfile=` MUST be cleared (empty assignment) AND the base
core-override.conf must be neutralized (bind-mount empty over it, or
remove it in core-base-desktop static/). An empty `AppArmorProfile=` in
/etc does NOT win over the base's /usr/lib drop-in — the base drop-in
is applied LAST in the merge order, so it must be removed, not just
overridden.

Critical gotcha #2: the unit has RefuseManualStart/RefuseManualStop, so
you CANNOT `systemctl --user restart` it to test. You must trigger a
fresh session (`sudo systemctl restart gdm` + autologin, or
logout/login) so the unit is born with the new label.

Critical gotcha #3: `systemctl --user` over SSH connects to a DIFFERENT
--user manager than the graphical session's manager. To inspect the
graphical session's units, either check /proc/<pid>/attr/current
directly (`pgrep -u your_username -x gsd-keyboard`) or use the
graphical session's manager. The SSH manager shows gnome-session
targets as inactive even when the graphical session is up.

Also found/fixed en route (important, separate issue):

The image was built with a STALE snapd (branch 26) missing the

Build gotchas for whoever picks this up:

- First boot has a ~4min cloud-init (cloud-final) delay before GDM;
  black screen during this is NORMAL, not a failure.
- The image is built WITHOUT --autologin by default; autologin config
  set via crudini/sed on the VM does NOT fire because GDM's autologin
  path needs the build-time gnome-session shim (--autologin flag). Use
  manual login, or rebuild with --autologin.
