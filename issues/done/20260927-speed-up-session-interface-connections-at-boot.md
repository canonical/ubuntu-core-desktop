# Reduce boot delay from session snap interface connections

## Impact / Priority

Medium-High. Users report that the VM takes several extra minutes to reach
the desktop because GDM waits for the
`ensure-desktop-session-connections.service` oneshot. Measure a fresh boot
from power-on through GDM/desktop readiness and record how much of that
time is spent in this service to confirm the end-user impact.

## Context

`ubuntu-core-desktop/build.sh` generates
`/etc/ensure-desktop-session-connections.sh` in
`gnome_write_session_connections()`. The script runs many `snap connect`
commands in sequence, with up to five retries and a three-second sleep
after each failed attempt. It connects both session-snap interfaces and
explicit desktop/Wayland/X11 connections for installed apps. The
generated `ensure-desktop-session-connections.service` is a oneshot,
ordered after snapd and `snapd.seeded.service`; a GDM drop-in explicitly
makes GDM wait for it.

That GDM ordering is intentional: previously, GDM could accept a login
while snapd was still updating the session snap's AppArmor profile after
one of these connections. GNOME session startup then failed against a
partially updated profile. Do not simply remove the GDM dependency or
move connections after login without testing this race.

## Recommendation

For the current development image, focus only on connections needed by
snaps included in the boot-time seed. Modify the snapd source used by
this project so gadget connection endpoints can explicitly reference a
snap by name when it has no asserted SnapID. Do not invent a fake
SnapID: preserve the existing ID-based behavior for asserted snaps, and
resolve name references only against snaps in the seed. Keep snapd's
normal endpoint validation and connection-policy checks. This should
let gadget seeding establish the required connections before GDM, while
avoiding the many serial `snap connect` subprocesses.

Do not expand this task to arbitrary snaps installed after first boot.
Keep the runtime script as a fallback until the seeded-image path is
verified end to end; then remove only the boot-time work it replaces.
Do not add `snap wait system seed`: `snap wait` accepts a snap name and
optional configuration key, and the unit already orders after
`snapd.seeded.service`.

## Next steps

1. Record a fresh-boot baseline for the connection service, GDM, and
   desktop readiness. Confirm which connections are required for the
   snaps present in the image seed; defer post-boot/optional-install
   behavior.
2. In the project snapd source, add and unit-test explicit name-based
   gadget endpoint references for seed-local snaps with no SnapID.
   Verify missing names/endpoints fail or skip safely, existing
   SnapID-based references are unchanged, and the standard connection
   policy remains enforced.
3. Declare the required boot-time connections in the GNOME gadget
   configuration generated by `ubuntu-core-desktop/build.sh`. First
   validate with focused snapd/parser/seeding tests to avoid repeated
   full image builds; then build the snap/image once for fresh-seed
   integration testing.
4. Verify on a fresh GNOME image that all required connections and
   AppArmor profiles are ready before GDM, then confirm login, desktop
   startup, display access, and Snap Store launch. Only after that,
   remove the corresponding runtime `snap connect` calls and compare
   boot time with the baseline.
5. If snapd state must be inspected before SSH becomes available, add
   QEMU's
   `-serial "unix:${SERIAL_SOCKET},server=on,wait=off"`
   to the QEMU boot invocation (as the KDE run setup already does) and
   capture the seed and service startup output from the serial socket.

## Resolution (2026-09-27)

Added snap-name gadget connection references to snapd for seed-time
connections involving local snaps without SnapIDs, retaining existing
SnapID and `system` references. Added parser and seeding tests, including
a local no-SnapID connection case. The GNOME build now declares its
session, broker, seeded Snap Store, and optional Firefox connections in
the gadget metadata and no longer generates the serial runtime
connection service or GDM drop-in. KDE's runtime connection path is
unchanged. The GNOME run setup now exposes the early boot serial console
on a Unix socket.

Validation: `go test -mod=mod ./gadget ./overlord/ifacestate` passed;
the snapd snap and a fresh GNOME image built successfully. The VM
reached `graphical.target` in 56.4 seconds, with `snapd.seeded.service`
taking 41.0 seconds. GDM started after seeding, the GNOME user session
and session manager were active, and gadget connections for the session
snap, broker, and Snap Store were present. The generated runtime
connection unit was absent, and launching Snap Store from the session
ran through the 15-second smoke-test window until intentionally stopped
by the timeout.
Commit references: `ubuntu-core-desktop` 495f774 and
`ubuntu-core-desktop-snapd` 9bc82d640b.

## KDE follow-up (2026-09-27)

Applied the same seed-time connection approach to the KDE gadget
generated by `ubuntu-core-desktop/build.sh`, removing the generated
`ensure-plasma-session-connections.service` and its GDM drop-in. The
custom snapd changes are shared with GNOME. The KDE component builds
completed successfully.

On a fresh KDE image, boot took 4m21s and `snapd.seeded.service` took
2m22.6s. GDM started after seeding, the runtime connection unit was
absent, and all available expected session, display, content,
network-manager, Avahi, and Bluetooth connections were reported with
`gadget` as their source. CUPS has no seeded provider, so its plug
remains unconnected.

The first KDE image did not reach a verified usable session:
`plasma-ksplash.service` timed out while KWin was not starting.
Follow-up debugging found that the `systemd-user-control` AppArmor
policy granted the session manager's unit-control calls only to the
GNOME session leader.

On the later image, KWin started with the DRM backend, Plasma Shell
became active, and KSplash completed. Further checks found KSMServer and
two X11 helpers crash-looping because the user systemd manager did not
have `DISPLAY`, `WAYLAND_DISPLAY`, or `XAUTHORITY`; KWin's attempts to
publish those variables were denied by AppArmor. In the running VM,
setting those variables in the user manager and restarting the failed
units made KSMServer, `gmenudbusmenuproxy`, and `xembedsniproxy` all
start successfully.

The source fix grants only the KWin app the
`UpdateActivationEnvironment` and `SetEnvironment` calls needed to
publish the session display environment, and orders the X11 helpers
after KWin. The focused snapd interface tests pass; updated snapd and
Plasma session snaps build successfully.

Clean-boot validation with a newly rebuilt KDE image confirmed that the
user manager populated `DISPLAY=:0`, `WAYLAND_DISPLAY=wayland-0`, and
`XAUTHORITY` without manual intervention. KWin and Plasma Shell were
active; KSMServer and both X11 helpers were active; KSplash completed
successfully; `graphical-session.target` was active; none of these units
appeared in the failed-unit list. No KWin environment-update AppArmor
denials or Plasma output readiness timeout appeared. Plasma Shell still
logged a Mesa EGL warning and `requesting unexisting screen geometry
-1`; QEMU could not attach to the host display from the automation
environment, so visual rendering was not independently confirmed.

The KDE startup fixes are committed in `ubuntu-core-desktop-snapd`
c675c97fb1 and `plasma-desktop-session` 5178930.
