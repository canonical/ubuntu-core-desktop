# gnome-terminal-server's wayland-client plug has no persistent auto-connect

Date: 2026-09-16

## Impact / Priority

Terminal fails to launch on any from-scratch image build: the
`wayland-client` connection is never made automatically, only manually
during ad-hoc testing on a long-lived test VM. No priority level was
stated in the original note; impact derived from the original note's
described symptoms.

## Context

Found as a follow-up while verifying
`20260916-confine-gnome-session-user-units.md` (the gnome-session/
gnome-shell confinement fix) end-to-end on a from-scratch image build.
Not caused by, and not part of, that confinement work -- a separate,
narrower gap in `ubuntu-desktop-session-snap`'s own interface wiring.

## What's missing

ubuntu-desktop-session-snap's `snap/snapcraft.yaml` (currently
uncommitted, part of the still-in-flight, out-of-scope changes tracked
under `20260915-followup-confined-session-apparmor-gaps.md` item 1)
declares a `wayland-client` plug on the `gnome-terminal-server` app:

    gnome-terminal-server:
      ...
      plugs:
        - wayland-client
    ...
    plugs:
      wayland-client:
        interface: wayland

This plug needs to be connected to `ubuntu-desktop-session:wayland` (the
SAME snap's own `wayland` slot) for `gnome-terminal-server` to reach the
compositor. This is a same-snap plug-to-slot connection, not a
cross-snap one -- it should always be connectable at boot, since
`ubuntu-desktop-session` is always installed (no install-order/timing
risk the way the Firefox/App-Center case has, see
`20260915-app-center-installed-snaps-need-desktop-interface-connections.md`).

Currently this connection is only ever made manually
(`snap connect ubuntu-desktop-session:wayland-client
ubuntu-desktop-session:wayland`) during ad-hoc testing on a long-lived
VM, and is lost on any fresh image build/boot. Without it, Terminal
fails to launch on a from-scratch image.

## Fix (straightforward, low-risk)

Add this connection to the existing boot-time connection workaround
already used for other same-snap-lacking-snap-id connections: the
`ensure-desktop-session-connections.sh` heredoc generated by the image
build (`build.sh`) (search for the
`for plug in ... snap connect "ubuntu-desktop-session:${plug}"` loop) --
add `wayland-client` to that loop, or add an explicit
`"ubuntu-desktop-session:wayland-client ubuntu-desktop-session:wayland"`
entry alongside the existing snap-store/firefox cross-snap connections
right after it. This is a small, mechanical, low-risk fix using the fast
dev-iteration loop already documented in
`20260916-confine-gnome-session-user-units.md` (edit the image build's
CORE_SNAP unpack/customize section -- no `core-base-desktop` rebuild
needed for this specific fix, since the connection script lives in the
image build itself).

Once ubuntu-desktop-session-snap's pending `wayland-client` plug change
(currently uncommitted, out of scope for this note) is itself committed,
the real long-term fix should be a proper gadget.yaml static connection
once the snap has a genuine store snap-id -- this boot-time script is
the same kind of interim, snap-id-independent workaround already used
for the ~24 other interfaces in that same script.

## Validation

1. Fresh image build + boot (not a long-lived/manually-patched VM), real
   or autologin session (per the documented confined-session login
   technique, `tools/confined-autologin-test.sh`).
2. Launch Terminal without any manual `snap connect` step.
3. Confirm `snap connections ubuntu-desktop-session` shows
   `wayland-client` connected to `ubuntu-desktop-session:wayland`
   automatically, with no manual intervention.
4. Full reboot regression test, not just a live session restart.

## Correction (2026-09-16, later)

The first attempt at this fix (adding `wayland-client` to the
single-arg same-snap loop, alongside account-control/hardware-observe/
etc.) did NOT actually work: those other entries are system-provided
implicit slots, but `ubuntu-desktop-session:wayland` is a slot provided
by the SAME snap as the plug. The single-arg
`snap connect ubuntu-desktop-session:wayland-client` form does not
resolve to the snap's own slot -- it instead tried to match the "snapd"
pseudo-snap and failed ("error: snap \"snapd\" has no \"wayland\"
interface slots"), leaving wayland-client permanently unconnected on
every boot.

Also, the ubuntu-desktop-session-snap plug/run.sh changes referenced
above as "pending .. currently uncommitted" were subsequently committed
(80bc822 in ubuntu-desktop-session-snap), but the prebuilt
`ubuntu-desktop-session.snap` consumed by the image build is a separate
cached artifact that is NOT automatically rebuilt from that source --
the ubuntu-desktop-session-snap repo's own build must be re-run and its
output snap copied into the image repo's `ubuntu-desktop-session.snap`
before an image rebuild will actually include any
ubuntu-desktop-session-snap source change. This tripped up validation
more than once; worth remembering for any future fix to that snap.

Fixed properly by moving `wayland-client` into the two-sided
`for connection in ...` loop (same explicit-both-sides form used for
snap-store/firefox), as `"ubuntu-desktop-session:wayland-client
ubuntu-desktop-session:wayland"`. Committed as 5dcddb5 in
ubuntu-core-desktop. Verified on a genuinely fresh rebuild+boot (with
ubuntu-desktop-session.snap also freshly rebuilt from source):
`ensure-desktop-session-connections.service` exits 0/SUCCESS, and
`snap connections ubuntu-desktop-session` shows `wayland-client`
connected to `ubuntu-desktop-session:wayland` automatically with no
manual `snap connect`. No AppArmor DENIED entries for
gnome-terminal-server in the boot journal.
